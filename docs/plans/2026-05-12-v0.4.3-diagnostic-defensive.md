# v0.4.3 — Diagnostic + defensive patch

Date: 2026-05-12
Status: approved, ready for implementation

## Problem

Issue #6 follow-ups (post-v0.4.2): two users report a reproducible "second-ride freeze" — first ride after install works, every subsequent ride freezes the instant the Start button is pressed. Live data fields keep showing the *last* value they ever displayed, indefinitely.

Cleanup audit of the v0.4.2 codebase identified:

1. `TymewearData` StateFlows (`_breathRate`, `_smoothBreathRate`, `_tidalVolume`, `_smoothTidalVolume`, `_minuteVolume`, `_smoothMinuteVolume`) are never zeroed when the BLE connection drops. `setDisconnected()` clears `brBuffer` and `tvBuffer` and toggles `_isConnected`, but the user-facing StateFlows retain their final pre-disconnect value. DataType collectors keep emitting that value forever. This is what makes a disconnect *look* like a freeze.
2. We dispatch `RequestBluetooth(extension)` exactly once in `onCreate`. If Karoo re-arbitrates Bluetooth on ride start (giving its own HR/power sensors priority), our extension's BT slot may be revoked without a `Disconnected` event being delivered. Leading hypothesis for the underlying cause.
3. No diagnostic trail exists for users who *can* run `adb logcat`. We can't tell from a remote report whether the BLE actually dropped, whether `RideState` transitioned, or whether notifications simply stopped firing.

We cannot confirm root cause without on-device logs, which the affected users haven't been able to provide. This release is intentionally diagnostic + defensive: surface the failure mode honestly, re-assert BT ownership on ride start, and add the log lines we'll need next time.

## Scope

In scope:

1. **Zero StateFlows on disconnect.** Add `_breathRate.value = 0.0`, `_tidalVolume.value = 0.0`, `_minuteVolume.value = 0.0`, `_smoothBreathRate.value = 0.0`, `_smoothTidalVolume.value = 0.0`, `_smoothMinuteVolume.value = 0.0` to `TymewearData.setDisconnected()`. Frozen-looking values become `0` or `--` on screen, signalling "connection lost" honestly.
2. **Re-dispatch `RequestBluetooth` on `RideState.Recording`.** Add a collector in `TymewearExtension.onCreate` filtered to `RideState.Recording` with `distinctUntilChanged`, dispatching `RequestBluetooth(extension)` on each transition. Idempotent per SDK docs.
3. **Diagnostic logging.** Add `Timber.d("RideState transition: $state")` in the new RideState collector. In the wrapped Emitter's `setCancellable` block in `TymewearExtension.connectDevice`, log `Timber.d("Wrapped emitter cancelled for $uid")` before the inner cancel fires — so we can see whether Karoo cancels the connect emitter on ride start.

Not in scope:

- DataType-level disconnect handling (showing "SEARCHING" badge on data fields). Out of scope; the value zeroing is sufficient signal for now.
- HR-collector leak when `karooSystem.connect` fires multiple times. Real but minor; defer.
- `Protocol.prevTimestamp40ms` reset on ride start. Real but minor; defer.

## Success criteria

- A connection drop produces visible "0" or "--" on the data fields within a few seconds, not the last cached value.
- If our underlying hypothesis is right, re-dispatching `RequestBluetooth` on ride start prevents the BT-arbitration revoke, eliminating the freeze.
- Any user willing to run `adb logcat -s "Tymewear:*"` produces a forensic trail of RideState transitions and emitter cancels.

## Implementation

Three commits + version bump.

### Commit 1 — Zero StateFlows on disconnect

`app/src/main/kotlin/com/tymewear/karoo/TymewearData.kt`

Replace the body of `setDisconnected()`:

```kotlin
fun setDisconnected() {
    _isConnected.value = false
    _batteryPercent.value = -1
    brBuffer.clear()
    tvBuffer.clear()
    // Zero the user-facing flows so a dropped connection shows "--" instead
    // of the last cached value (which looks like a freeze).
    _breathRate.value = 0.0
    _tidalVolume.value = 0.0
    _minuteVolume.value = 0.0
    _smoothBreathRate.value = 0.0
    _smoothTidalVolume.value = 0.0
    _smoothMinuteVolume.value = 0.0
}
```

Commit message: `Zero StateFlows on disconnect so a dropped connection shows "--" not stale value`

### Commit 2 — Re-dispatch RequestBluetooth on ride start

`app/src/main/kotlin/com/tymewear/karoo/TymewearExtension.kt`

In `onCreate`, inside the existing `karooSystem.connect { connected -> if (connected) { ... } }` block, after the existing HR collector launch, add a second collector:

```kotlin
scope.launch {
    karooSystem.consumerFlow<RideState>()
        .distinctUntilChanged()
        .collect { state ->
            Timber.d("RideState transition: $state")
            if (state is RideState.Recording) {
                Timber.d("Recording started — re-dispatching RequestBluetooth")
                karooSystem.dispatch(RequestBluetooth(extension))
            }
        }
}
```

Imports to add at the top of the file:
- `kotlinx.coroutines.flow.distinctUntilChanged`

The `Timber.d("RideState transition: ...")` line on every transition (not just Recording) serves as the diagnostic trail.

Commit message: `Re-dispatch RequestBluetooth on ride start; log RideState transitions`

### Commit 3 — Log wrapped emitter cancellation

`app/src/main/kotlin/com/tymewear/karoo/TymewearExtension.kt`

In the `wrapped` Emitter's `setCancellable` override (inside `connectDevice`), add a log line at the start of the lambda:

Current:
```kotlin
override fun setCancellable(cancel: () -> Unit) {
    emitter.setCancellable {
        try { cancel() } finally {
            if (activeConnections.decrementAndGet() == 0) {
                Timber.d("Last active connection closed — scheduling debounced stop")
                scheduleForegroundStop()
            }
        }
    }
}
```

New:
```kotlin
override fun setCancellable(cancel: () -> Unit) {
    emitter.setCancellable {
        Timber.d("Wrapped emitter cancelled for $uid")
        try { cancel() } finally {
            if (activeConnections.decrementAndGet() == 0) {
                Timber.d("Last active connection closed — scheduling debounced stop")
                scheduleForegroundStop()
            }
        }
    }
}
```

Commit message: `Log wrapped emitter cancellation for forensic trail`

Release notes:

```
Diagnostic + defensive patch addressing the "second-ride freeze" pattern reported on Karoo 3. Three changes: (1) dropped connections now show "--" on data fields instead of the last cached value, so disconnects are visible; (2) Bluetooth ownership is re-requested on every ride start, defending against Karoo's BT arbitration silently revoking the extension's slot; (3) extra log lines for forensic capture via adb logcat. This release does not claim to fix the underlying connection issue — it makes it visible and adds defensive plumbing while we gather diagnostic data from affected users.
```

Commit message: `Bump version to 0.4.3 (versionCode 9)`
